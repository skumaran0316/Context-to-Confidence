RESULT

One entry, counted twice

One $60,000 revenue entry has two supporting notes. The query counted the entry once per note.

Joining two evidence links repeats the same accounting entry
Accounting entryEvidence linkAmount counted
REG-Q3-001LINK-A$60,000
REG-Q3-001LINK-B$60,000

Expected: $1,020,000 + $60,000 = $1,080,000.

Observed: $1,020,000 + $120,000 = $1,140,000.

The source entry is unique. The one-to-many evidence join duplicates it before aggregation. Q2 has no duplicated links.

Before

The query matches the $60K entry to two notes, then adds up both rows.

entries
  LEFT JOIN evidence_links USING (entry_id)
  → SUM(amount_usd) by quarter

Fix

Add up the accounting entries first. Fetch the notes separately so they can’t change the total.

entries → SUM(amount_usd) by quarter
  → retrieve evidence separately

PRESENTER NOTES

One question. Five steps.

  1. Ask & check. Start with the CFO’s team-chat request and prefilled question. Send, choose whether to trust the answer, then compare bookings with recognized revenue.
  2. Prepare context. Introduce trusted data, business definitions, contextual evidence and evaluation. Prepare reveals the details. Evaluation references remain outside agent context; the architecture disclosure shows the data path and feedback loop.
  3. Compare answers. Send the same question with the approved definition and linked account evidence. A better answer still needs validation.
  4. Run an eval. Compare both answers with the independent reference across metric selection, numerical accuracy, evidence coverage, groundedness and causal restraint.
  5. Catch a regression. A duplicate join counts one $60K entry twice: Q3 becomes $1.14m, down 5%, instead of $1.08m, down 10%. Run the eval, inspect the query, apply the fix, explicitly rerun the answer and reevaluate against the unchanged reference.
